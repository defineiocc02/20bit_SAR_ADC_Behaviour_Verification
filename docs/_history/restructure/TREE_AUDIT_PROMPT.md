## 二、你的任务

对该仓库做**完整的工作树结构审查与版本一致性审查**。
**不是审查算法正确性，不是审查后端结果，只审查"文件与版本管理"这一层。**

### 任务 1：识别真实的"现行版本"与"历史版本"

**问题**：仓库里有多少个模块/脚本/文档存在**多个版本并存**？

**必须给出**：

1. 逐一列出所有**同名不同版**的候选（如 `X.py` 与 `X2.py`、`X_v1.md` 与 `X_v2.md`、
   `X.sv` 与 `X_new.sv` 等）。
2. 对每一组，用 `grep -r` 或 `import` 分析**判断哪个是现行、哪个是历史**。
3. **明确说明你的判断依据**（引用次数？被谁引用？文件内自述？）。

**禁止**：仅凭文件名或日期判断。

### 任务 2：核查"归档"是否真的安全

对 `rtl/_legacy/`、`tools/_legacy/`、`docs/_history/` 三个归档区：

1. **归档区的文件是否仍被活动代码引用？**
   用 `grep -r "<文件名>" tb/ tools/ src/ flow/ formal/ 2>/dev/null` 逐个核查。
2. **是否有活动代码仍在引用归档区路径？**
3. **是否有文件存在"半归档"状态**（如 A 目录的脚本引用 B 目录的 _history 文件）？

**输出**：一个"归档安全性"表格，标注每种情况是安全/不安全。

### 任务 3：核查文档自述与实际的一致性

仓库有多份声明"自己是唯一权威"或"索引"的文档：

```
README.md                   （根目录）
docs/STATUS.md              （自称"单一权威版本"）
docs/INDEX.md               （自称"docs 总索引（权威）"）
docs/audit/README.md        （审计索引）
rtl/README.md               （RTL 索引）
docs/CONTRACT_CURRENT.md    （自称"当前合同入口（唯一）"）
```

**核查**：

1. 每一份的**版本字段/日期**是否与当前 HEAD 一致？
2. 每一份声称的**文件数量、目录结构**是否与实际 `find`/`ls` 结果一致？
3. **交叉引用是否有死链**？
4. **是否有两份文档对同一事实给出不同说法**？（这是最严重的问题）

**必须给出**：不一致之处的**原文引用 + 实际值**对照。

### 任务 4：核查四个顶层的关系

**背景**：此前有四个 RTL 顶层并存，最近归档了三个，只留
`rtl/v21/adc_digital_ip_v21.sv`。

**核查**：

1. 归档的三个顶层（`rtl/_legacy/tops/`）**是否真的有测试台或脚本在用**？
2. 现行顶层**实例化了哪些模块**？**哪些模块从未被任何顶层实例化**？
3. **是否存在"孤儿模块"**（有 RTL、有 Formality 证据、但没有任何顶层使用）？

**这一条尤其重要**：孤儿模块意味着"验证过了但没接上"。

### 任务 5：核查版本控制卫生

1. **`.gitignore` 是否漏掉了应该忽略的产物**？
   （检查仓库里是否有 `*.log`、`*.vcd`、`*.fsdb`、`__pycache__`、
   `*.pyc`、临时目录等被意外跟踪）
2. **是否有大文件**（>1MB）被跟踪？逐个列出并说明是否必要。
3. **是否有敏感信息**（路径中的用户名、绝对路径、license 路径）？
4. **提交历史**：是否有重复提交、回退痕迹、WIP 提交？
