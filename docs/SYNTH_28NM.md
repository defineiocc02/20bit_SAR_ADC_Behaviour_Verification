## 系数存储占比

系数表 = 18 片 × 20 单元 × 44 bit = 15,840 bit，加 `g_tab` 18×44 = 792 bit，
合计 **16,632 bit**，占 18,079 个时序单元的 92%。

按比例折算：

```
系数存储 ≈ 30,076.59 × (16632 / 18079) = 27,670 µm²
占总面积 27,670 / 99,195.8 = 27.9%
```

**回答"16k 系数触发器占多少"：约 27.9%，即 0.0277 mm²。**

## 需要处理的问题

1. **Hold −0.03 ns 违例**：量级很小，通常由布线前时钟树理想化导致，
   插入延时单元或 CTS 后一般可消；但**当前状态确实违例，不能报 PASS**。
2. Setup 余量 16.51 ns 说明 25 ns 约束对 28 nm 过于宽松。
   若要评估真实能力，应另跑一版 5 ns / 2 ns 约束（探索性，不计入签核）。
3. 系数表用触发器，`Noncombinational area` 30,077 µm² 中 92% 是它。
   换 512×72 SRAM 宏可大幅压缩，但要先验证读取带宽。

# Hold 修复尝试（2026-11-14，**未成功**）

做法：`compile_ultra -gate_clock` → `set_fix_hold [get_clocks clk]` →
`compile_ultra -incremental -gate_clock`。原始报告 `synth/results/w28_holdfix/`。

| **Hold 违例路径数** | — | **118** | **未归零** |
| 违例网络数 | — | 25 | — |
| 最大转换违例 | — | 25 | 新增发现 |
| Setup WNS | +16.51 ns | +16.49 ns | 略降 0.02 |
| 总单元面积 | 99,195.80 µm² | 100,324.56 µm² | **+1,128.76（+1.14%）** |
| 单元数 | 150,073 | 154,106 | +4,033 |

## 判定：**FAIL**

按验收口径（不以脚本跑完为 PASS）：

- Hold WNS **仍为负**（−0.03）
- TNS **−3.10 ns，非零**
- 违例路径 **118 条，未归零**
- Setup 略恶化（+16.51 → +16.49），面积 +1.14%

## 原因分析

时钟仍是**理想时钟树**（未 `set_propagated_clock`）。
在理想时钟下，DC 对同一时钟域内的短路径只能靠插延时单元，
但对 16k 触发器阵列的大量短路径，`set_fix_hold` 的效果有限。

**这不构成架构错误的证据。** 真实 hold 需在 CTS 后用实际时钟插入延迟评估，
那时有真实的 skew 与 uncertainty 分配，很多当前的"违例"会重新分布。

## 另需注意

`Max Trans Violations: 25` —— 有 25 条网络的最大转换时间超限，
这在布线前就该处理（加 buffer 或调扇出），不应留到后面。
