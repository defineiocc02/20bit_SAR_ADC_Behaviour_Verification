## 3. 为什么 `wsum` 这么大

```systemverilog
// wsum_v21.sv 的三个函数
f_G  : for s(8) × for j(16) -> wt_main[ids[s*5+:5]][j]
f_Wm : for s(8) × for j(16) -> 条件累加
f_Wp : for s(8) × for j(4)  -> 条件累加
```

每笔交易要读 **8 slot × 16 列 = 128 个 40 位权重**，
每个 `ids` 是 5 位索引指向 18 项数组 →
**128 × 18 = 2,304 路候选，每路 40 位 = 92,160 个 MUX 输入**。

三个函数（G/Wm/Wp）各自独立做这件事，等于 **3 × 92,160 ≈ 276,480 个 MUX 输入**。

**改成内部寄存器堆后查表逻辑没变，只是输入从端口变成寄存器。**

## 4. 可行的优化方向（不改算法）

| 方向 | 做法 | 预期收益 | 风险 |
|:---|:---|:---|:---|
| **A** | 三个函数**共用一次查表**：先按 `ids` 取出本笔 8×16 的权重到临时寄存器，G/Wm/Wp 都从这份读 | 大幅减少 MUX（3 次 → 1 次） | 需要一拍额外延迟或组合路径变长 |
| **B** | 把 18×16 二维表**展平成一维 [288]** | 少一级索引 | 收益中等 |
| **C** | 用 `case (sid)` 展开 18 个分支 | DC 可能更易优化 | 代码量大 |
| **D** | 权重表用**单端口 SRAM**（而非寄存器堆） | 面积小得多 | 需要 memory compiler，超出当前范围 |

**方向 A 收益最大且不改算法**：现在 `f_G`/`f_Wm`/`f_Wp` 各查一次表，
而它们读的是**同一份** `wt_main[ids[s]][j]`。
