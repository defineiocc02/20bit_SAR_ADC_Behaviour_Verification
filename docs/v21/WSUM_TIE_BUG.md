# 撤回：「wsum_v21 权重被综合折叠」是错误结论（测试接线接反）

时间：2026-11-16　基线：`c801a62`　裁定：**定论撤回**

## 1. 结论先行

**此前"`wsum_v21` 只有 `sid=17` 的权重参与求和、`sid=0..16` 被综合折叠"
的定论是错的。**

真实原因：**我做门级测试时的权重表位序接反了。**

修正接线后，同一份旧网表（`/tmp/wsum_evidence/wsum_only.v`）
在 **364 笔 × 3 字段完整比对下 0 处不符**，且每笔都与独立整数参考值一致。

## 2. 错在哪

DC 把权重表展平成扁平拼接端口，源文件写作：

```verilog
.w_main_tbl({ \w_main_tbl[0][0][39] , \w_main_tbl[0][0][38] , ... })
```

Verilog 拼接 `{a, b, c}` 中 **`a` 是最高位**，所以：

| 端口 | 扁平向量位置 |
|:---|:---|
| `\w_main_tbl[0][0][39]` | **bit 11519（MSB）** |
| `\w_main_tbl[17][15][0]` | **bit 0（LSB）** |

**我的 v1.0 打包写成了：**

```systemverilog
w_main_flat[(s*16 + j)*40 +: 40] = w_main_tbl[s][j];   // 错！
// s=0,j=0 -> bits[39:0]，即最低 40 位
```

把 `[0][0]` 放到了**最低位**，行列顺序整个接反。

**正确写法：**

```systemverilog
w_main_flat[11519 - (s*16 + j)*40 -: 40] = w_main_tbl[s][j];
w_sub_flat [2879  - (s*4  + j)*40 -: 40] = w_sub_tbl [s][j];
```

## 3. 为什么接反会伪装成"折叠"

接反后，`ids=0` 时测试实际上访问的是**另一行**（最后一行 `sid=17`）。
所以现象是"只有一行有响应"，看起来完全像"综合把 17 行折叠了"。

我据此写了 §10 的"逐 slice 扫描"和 §10.3 的
"`G = 8*16*(2^40-1)` 精确吻合"——那个"精确吻合"恰恰是因为
**8 个 slot 都指向同一行、16 列全 1**，不管指向哪一行，结果都是
`8*16*(2^40-1)`。**这个"证明"从一开始就不成立。**

## 4. 撤回的具体条目

| 原定论 | 状态 |
|:---|:---|
| §1「`wsum_v21` 网表输出恒为 0」 | **撤回**（是测试接线错误） |
| §2「最小用例 RTL 8192 vs 网表 0」 | **撤回**（网表侧权重写到了错误的行） |
| §3「TIEL 驱动 G_q30 高位」 | 现象真实存在，但**它是合法的常量优化**（见 §5），不是缺陷 |
| §10「只有 `sid=17` 有效」 | **撤回**（是接反的表现） |
| §10.3「`8*16*(2^40-1)` 精确吻合」 | **撤回**（对该结论无鉴别力） |
| §11「钳位修复安全性论证」 | 论证本身成立（合法域零改变），但**它不能证明修了什么缺陷** |

## 5. TIEL 单元与 OPT-1206 是合法的

修好接线后，`w_main_tbl` 的第 17 行在 `ids` 只取 0..17 时确实参与运算，
但网表里 `G_q30` 高位接 `TIEL`、`dc.log` 里部分 `G_q30_reg[*]` 被
`OPT-1206` 删除 —— **这些是合法的常量优化**：

- 权重表是 Q30 定点，18 行 × 16 列 × 40 位，实际位宽远小于 64
- 高位在合法权重范围内恒为 0，DC 删除它是正确的

类似 `recip_q60` 的 `u0_r_reg[30]`：LUT 值域 `max = 1065418243 < 2^30`，
bit 30 恒 0，删除正确。

**判断标准**：常量优化是否合法，要看**该位在合法输入域内是否恒定**，
不能只看"有 TIEL 单元"就认定是缺陷。

## 6. 修正后的验证（这是本轮唯一可信的 wsum 证据）

测试台 `tb/v21/tb_wsum_scan.sv` v2.0，共 364 笔：

| 阶段 | 内容 | 笔数 |
|:---|:---|--:|
| 1 | 18 行分别写互不相同权重，全 slot 全掩码 | 1 |
| 2 | **逐行逐列单点非零扫描**（`w_main`） | 18×16 = 288 |
| 3 | **逐行逐列单点扫描**（`w_sub`） | 18×4 = 72 |
| 4 | 8 个互异合法片号 + 有区分度的 pre/post 图案 | 3 |

每笔都带**独立整数参考值**（`rG/rWp/rWm`）并当场比对，
输出含 X/Z 立即报错。

结果：

```
RTL  : 364 笔，errors=0
网表 : 364 笔，errors=0
交叉比对：364 笔 × 3 字段，G/Wp/Wm 各 0 处不符
交易号集合相同（无缺笔、无重复）
```

**`wsum_v21` 的功能在任意权重下 RTL 与网表一致。**

## 7. 对 `385d286`（SID 钳位）的处理

审查裁定：「钳位在合法输入下不改变 RTL，只能说明候选的合法域行为保持；
不能证明它修复了综合缺陷。暂不扩展，也不要盲目回退。」

**采纳。** 现状：
- 钳位代码保留在工作区，**不再作为"修复缺陷"宣称**
- 它带来的整核综合超时（>30 min 未出网表）**不作为证据**，
  也不能归因为"组合复杂度增加" —— 我没有错误码或退出码支持这个说法
- 待用正确接线重跑同版综合后再决定去留

## 9. 教训

1. **映射必须从实际网表端口名生成并自检，不能猜展开顺序。**
   现在 `gen_wsum_gate_tb.py` v2.0 会打印并校验
   `首 [0][0][39] / 末 [17][15][0]`，不符就报警。
2. **"精确吻合"可能是伪证据。** `8*16*(2^40-1)` 那个等式对
   "哪一行被选中"不敏感，所以它证明不了任何行列正确性。
3. **测试接反会伪装成工具缺陷**，而且伪装得很像 ——
   因为"只有一行响应"正是"17 行被折叠"的预期表现。
