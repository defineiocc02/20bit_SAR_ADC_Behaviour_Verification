## 1. 现象

`sched18` 完整 RTL-to-GDS 只用约 **3 分钟**（综合 50 s + 布局/CTS/布线 90 s），
Formality `SUCCEEDED`。

`wsum_v21` 同流程已运行 **22 分钟以上**仍未完成，当前在 `initial_place / Initial Placement`。

## 3. 根因

`wsum_v21` 的权重查表结构：

```systemverilog
cur_main[s][j] = wt_main[ids_i[s*5 +: 5]][j];   // 8 slot × 16 列 × 18 行
```

每笔交易要从 **18 行**里按 **5 位索引**选出 **8 行**，每行 **16 列 × 40 位**：

```
8 × 16 × 18 = 2,304 路候选
2,304 × 40 位 = 92,160 个 MUX 输入
```

这不是"代码写错"，而是**数据结构选择导致的门级规模**。

## 4. 三个独立工具的交叉验证

| 工具 | 结果 | 一致性 |
|:---|:---|:---|
| **DC 综合** | 515 s / 153,735 cells | — |
| **FC compile_fusion** | 1,150 s / 34 轮优化 | ✅ 同样慢 |
| **FC placement** | > 4 分钟仍在 coarse/DTDP | ✅ 同样重 |

**三个独立测量都指向同一结论：`wsum` 的门级规模使物理实现代价不可接受。**

## 5. 这不是配置问题

已排除：
- ❌ 时钟门控（已禁用）
- ❌ 库配置（`.tf` + tech LEF 已验证，`sched18` 同配置 3 分钟跑通）
- ❌ VA/UPF（`sched18` 同配置通过）
- ❌ site row（`sched18` 同配置通过）

**唯一变量是 RTL 规模。**

## 6. 结论与选项

**结论**：`wsum_v21` 用当前的"寄存器堆 + 二维数组查表"结构，
在 28HPC+ 上的物理实现代价远超可接受范围。

| 方案 | 做法 | 预期 |
|:---|:---|:---|
| **A** | 用单端口 SRAM 替代寄存器堆 + 查表 | 面积降一个量级，但需 memory compiler |
| **B** | 把 18×16 表展平为 [288] 一维，减少索引级数 | 收益有限（MUX 总量不变）|
| **C** | 改变算法：不在每笔交易查全表，改为增量更新 | 需重构 D5，且要重跑全部回归 |
| **D** | 接受现状：`wsum` 只做 DC 综合与功能验证，不做物理实现 | 交付不完整但诚实 |
