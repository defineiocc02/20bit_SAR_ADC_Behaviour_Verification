# PPA 对照：64 位除法器 vs 倒数+修正

时间：2026-11-16　基线：`12e0c66`
工艺：TSMC 28HPC+ 7T `ssg0p81vm40c`　工具：DC W-2024.09-SP3
约束：`clk = 25 ns`，input/output delay 各 1.0 ns，`BUF_X2` 驱动，`0.05 pF` 负载

## 1. 对照对象

两者实现同一个功能：`I = RND(2^60, G)`，G ∈ [2^34, 2^36]。
唯一差异是求商的方式，其余逻辑（两次乘法、一次减法、最近舍入比较）完全相同。

| 版本 | 文件 | 求商方式 |
|:---|:---|:---|
| 除法器 | `div_ref.sv` | `q = 2^60 / G`（64/64 可配置除数） |
| 倒数+修正 | `recip_rnd_v21.sv` + `recip_q60.sv` | Newton 倒数 + 真实 G 算余数 + 双向夹逼 |

## 2. 结果

| 指标 | 除法器 | 倒数+修正 | 倍数 |
|:---|--:|--:|--:|
| **综合耗时** | **> 600 s 不收敛** | **31 s** | **> 19×** |
| cells | — | **443** | — |
| 面积 | — | **346.53 µm²** | — |
| 最差 slack @25 ns | — | **+23.37 ns** | — |
| 收敛性 | 卡在 `i_q60_reg[23]/D` | 正常结束 | — |

**除法器版连续三次（recon 顶层、recon 块级、div_ref 单模块）都卡在
同一个端点族 `i_q60_reg[*]/D` / `code_o_reg[*]/D`，每次超过 10 分钟。**

倒数+修正版 31 秒收敛，slack +23.37 ns，余量充足。

## 3. 为什么这个结论可信

**同一个 RTL、同一个库、同一个时钟角、同一套 IO 约束、同一个
`compile -map_effort medium`。** 唯一变量就是求商实现。

而且之前已有两条独立证据指向同一结论：

1. `CHECKPOINT_I5_SYNTH_v4.md`：把 recon 里两个除法器的**除数换成常数**
   后，综合从「>10 分钟不收敛」变成「秒级完成，4575 cells / 3468 µm²」。
   那次的对照说明"可配置除数是瓶颈"。
2. 本次对照说明"换成倒数+修正后，同功能实现只需 443 cells / 346.53 µm²"。

第三条证据（本轮新增）是目前唯一给出**可对比面积数字**的，
前两条只有"收敛/不收敛"的定性差别。

## 4. 功能等价性（替换的前提）

替换的前提是功能完全一致，这一点已有三层证据：

| 层 | 证据 | 规模 |
|:---|:---|:---|
| 算法 | `tools/check_recip_correction.py` | 50,013 样本失配 0 |
| 倒数 RTL | `tb_recip_q60` | 43,766 笔与 Python 模型逐位一致 |
| 修正 RTL | `tb_recip_rnd` | 20,817 笔与精确 `RND(2^60,G)` 逐位一致 |

三层都过，才做本次 PPA 对照。

## 5. 尚未做的（不能说"可以直接替换"）

| 项 | 状态 |
|:---|:---|
| 把 `recip_rnd_v21` 接进 `recon_v21` | **未做** |
| 替换后重跑 `tb_i4_recon`（8213 项）| **未做** |
| 替换后重跑 `tb_i4b_e2e`（25 项）| **未做** |
| 完整顶层综合 | **未做** |
| 后布线 STA / PPA | **未做** |

**关键风险**：`recip_rnd_v21` 的延迟与 `rnd64` 不同。

- `rnd64` 是纯组合，recon 的 S2 级用它
- `recip_rnd_v21` 自带 `recip_q60` 的两级流水 + 出口一拍 = **3 拍延迟**

替换后 recon 的流水拍数会变，`out_valid` 相对 `in_valid` 的延迟
也要跟着改（当前是 4 拍）。这影响 `tb_i4_recon` 和 `tb_i4b_e2e`
的时序期望，**必须一并调整并重新验证**，不能只换模块。
