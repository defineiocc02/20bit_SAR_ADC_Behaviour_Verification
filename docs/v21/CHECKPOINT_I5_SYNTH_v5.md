## 1. 最重要的结果：综合收敛了

把 `recon_v21` 里 `I = RND(2^60, G)` 的 64 位可配置除数除法器
换成 `recip_rnd_v21`（Newton 倒数 + 余数修正 + 最近舍入）之后：

| 指标 | 替换前 | **替换后** |
|:---|:---|:---|
| `STEP_COMPILE_OK` | **从未出现**（三次超时，各 >10 min） | **出现** |
| 综合耗时 | > 1300 s（超时） | **583 s** |
| cells | — | **142,065** |
| Total cell area | — | **89,693.13 µm²** |
| 未时钟寄存器 | — | **0 / 1863** |
| 最差 slack | — | **+16.80 ns** |
| 关键路径 | 卡在 `i_q60_reg[*]/D` 不收敛 | `u_recon/x3_q_reg[31] → u_recon/code_o_reg[19]` |

**关键路径现在是真实算术路径**（X 到 code 的乘加与舍入），
不是之前那种寄存器自环。slack +16.80 ns 意味着 25 ns 周期下
余量充裕 —— 这也解释了为什么之前"卡住"：DC 在为一个本可以
轻松满足的时序反复优化一个巨大的除法器。

## 2. 替换做了什么

`recon_v21` 的流水从 4 拍变成 6 拍：

| 级 | 替换前 | 替换后 |
|:---|:---|:---|
| S1 | Y → Z | 同 |
| S2 | N 与 I（I 纯组合除法） | **S2a/S2b/S2c：N 打三拍，与 `recip_rnd_v21` 的 3 拍 I 汇合** |
| S3 | X = N·I >> 36 | 同 |
| S4 | Q → code | 同 |
| `out_valid` 延迟 | 4 拍 | **6 拍** |

`tb_i4_recon` 与 `tb_i4b_e2e` 的等待拍数已同步改为 6 拍。

## 4. 面积对比：必须谨慎解读

| 对象 | 面积 | 说明 |
|:---|--:|:---|
| 原型数字区 | **60,000 µm²** | **照片图估**，非标准单元面积 |
| 本工程完整顶层 | **89,693 µm²** | **标准单元综合面积** |

数值比 ≈ **1.49×**。

**但这个比值不能当作"我们差 1.5 倍"的结论**，原因有四：

1. **口径不同**：一个是版图区域估算，一个是标准单元面积，不含布线、
   不含宏、不含 IO。两者不能直接相减。
2. **范围未知**：原型红框内到底含哪些模块，原文没有披露。本工程的
   89,693 µm² 含 D1–D6 全部（sched18、两笔上下文、DEM、dither、
   wsum、recon、ADC2 捕获）。
3. **本结果未做面积优化**：`compile -map_effort medium`，无
   `-area_effort`、无时序驱动优化、无 retiming、无资源共享。
4. **未做层次边界优化**：`set_ungroup` 为默认，跨层优化空间未利用。

所以正确的表述是：**首次拿到完整顶层的标准单元面积 89,693 µm²，
它与原型图估数字区同量级（1.5× 内）；进一步的可比性需要统一口径。**
