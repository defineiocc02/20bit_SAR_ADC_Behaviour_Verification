# 生产 Python ↔ RTL 对拍：19/420 失配的定位

基线 `c151672`。**结论：RTL 侧自洽，差异在 Python 生产路径。**

## 独立复算（用探针向量里的 wm/g/inv/adc/dither）

```
wm=4825363371  g=34340654825  inv=33573079  adc=2000  word=44

I 重算 = 33573079                      与向量一致
num    = 6Wm−3G = -74069784249
d      = num*I >> 36 = -36186986       与 RTL 探针一致
r̂      = ((2·2000+1)·144+2)/5 = 115229 与 RTL 一致
t      = 44 × 24576 = 1081344          与 RTL 一致（此前的 56 是我手算错）
x      = -34990413                     与 RTL 一致
q      = -364483                       与 RTL 一致
code   = 524288 - 364483 = 159805      与 RTL 一致
```

**所以 RTL 的每一级都能用纯整数从头算出来，且与探针值逐位相同。**
期望值给的是 159804，说明 Python 生产路径输出的不是 159805。

## 因此

- 不是 RTL 实现错
- 不是 dither 位权错（先前判断有误，已更正）
- 是 `run_transaction()` 内部某处与"用导出字段重算"不等价

# 更正与落实（2026-11-14，按审阅要求）

## 1. 撤回：「19 条失配已定位为 T 位权不同」

**该结论错误，作废。** `c151672` 中 Python 与 RTL 的 Dither 表达式本来一致：

```
word=44 (101100)
  Python: U=5, L=0.5, total×8 = 44
  RTL   : t_num = 8·U + 16·D5 + 4·D2 + 2·D1 + D0 = 44
```

报告中出现的 `56` 是**我手算错了**（把 D5 位当成 D4 位代入）。

**64 个扰动字全部核对：`Python total×8 == RTL t_num`，不一致字数 0。**

Dither、余差项、最终舍入均**未修改**，也不需要修改。

## 2. 实际修复的只有一处：生产 Python 的整数表达式

改为直接使用循环内累加的 `Wm_q30`，不从 `K` 反推：

```python
dac_q24 = ((6 * Wm_q30 - 3 * G_q30) * inv_g_q60) >> 36
```

删除了旧的两段式 `wm_q30 = G//2 + (-K)//(2VR)` 与
`6*((wm*inv)>>36) - 3*2^24`。

`K` 保留为**独立一致性检查**，不参与 `D_eff`：

```
K_q54 == VR · (G_q30 − 2·Wm_q30)      420 组违例 0
```

## 3. 失败向量两端复核

```
dac_q24 = -36186986      RTL 探针 -36186986
x_q24   = -34990413      RTL 探针 -34990413
code20  =    159805      期望值    159805
```

一致。差异确实来自修复前 Python 侧的旧表达式，不是 Dither。

## 4. 回归

从修复后的 `run_transaction()` 重新生成 420 条期望值（向量未手改），
VCS 结果：**420/420 逐位一致，0 失配、0 溢出**。

同时验收第二条：倒数近似 ↔ 精确除法最大差 **1 个 Q24 单位 = 0.06 µV = 0.01 LSB20**。

## 5. 关于依据

「硬件自然实现」「旧生成器 400/400 通过」**都不能作为修改 SPEC 的理由**。
本轮改的是**生产代码去落实已冻结的表达式**，不是反过来改规格。
Dither 设计不再重开。
